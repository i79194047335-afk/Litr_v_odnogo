# WORKFLOW — организация работы в проекте

Как устроена работа: слои, кто что делает, когда обязателен протокол, как
пишутся и проверяются тулзы и агенты.

Правила поведения — в `CLAUDE.md`. Этот файл про организацию, не про поведение.

---

## 1. Три слоя

```
   топ-модель (Claude)      архитектура, ревью, фальсификация, суждение
        ↑ результаты, не сырьё
   узкие агенты             дешёвая модель + шелл, одна задача каждому
        ↑ отфильтрованное
   тулзы                    детерминированный код, ноль моделей
        ↑
   сырьё                    WS-лента, снимки доков, файлы на диске
```

**Правило слоёв:** снизу вверх поднимается только то, что нельзя решить ниже.

- Отбор, фильтрация, счёт, сверка, извлечение — **тулзы**.
- Суждение о смысле («ломает ли это интеграцию») — **агент**.
- Архитектура, спор о выводах, стратегия — **топ-модель**.

**Проверка на правильность разбиения:** если убрать модель из шага и результат
воспроизводится кодом — модель там лишняя.

## 2. Тулзы

### 2.1 Что это

Функция, которую модель может вызвать, но выполняет не она. Модель решает
**что** спросить; отвечает код. Ответ одинаков сегодня и через месяц.

### 2.2 Когда писать

**После второго ручного повторения.** Не раньше.

### 2.3 Требования (обязательные, каждое)

1. **Детерминированность.** Один вход — один выход. Никаких вызовов модели
   внутри тулзы.
2. **Явный отказ.** При несовпадении — ненулевой код возврата и внятное
   сообщение. Тулза, печатающая успех при неудаче, хуже отсутствия тулзы
   (прецедент: патч-скрипт, писавший «FAILED: found 0 matches» и продолжавший
   работу).
3. **Тест, который умеет краснеть.** Ожидаемое значение выведено из правил, а не
   считано с реализации. Проверяется намеренной поломкой.
4. **Портируемость заявлена.** Если написано «awk» — значит POSIX awk, и это
   проверено на mawk, а не только на gawk.
5. **Различимость своих ошибок и чужих.** «Инструмент сломался» и «источник
   изменился» должны давать разные сообщения (прецедент: mawk выдавал ноль
   страниц, а агент сообщал «Lighter сменил формат»).

## 3. Агенты

### 3.1 Форма

Агент — не сервис, а папка с файлами: скрипт, README, состояние, база знаний,
свои тесты. Модель удалённая, вычислительной нагрузки нет.

Эталон — `archivarius/`. Следующие агенты копируют его форму.

### 3.2 Обязательные свойства

1. **Одна узкая задача.** Расширение задачи — повод для нового агента, не для
   роста существующего.
2. **Дешёвая модель.** Топ-модель в рантайме агента не участвует.
3. **Фильтрация до модели.** Неизменившееся до модели не доходит. В обычный день
   стоимость близка к нулю.
4. **Файлы вместо базы.** Состояние — сами файлы; наличие файла и есть факт.
5. **Доказательство рядом с выводом.** Каждая запись несёт исходный фрагмент
   (`evidence`), иначе пересказ нечем перепроверить.
6. **Негодный ответ отбрасывается, а не записывается.** Молчание честнее мусора;
   страница откатывается и идёт на повтор.
7. **Два выхода обязаны сходиться по счёту.** Проза и машинный журнал — если
   числа разошлись, что-то потеряно молча.
8. **Тесты на копии состояния.** Тестовый прогон в постоянную базу знаний не
   пишет никогда. Если всё же пишет — с полем `"synthetic": true`.
9. **Свои тесты на режимы отказа.** Не только на успешный путь.

Замена модели обнуляет все измерения качества её ответов. Прежнее число
(10 негодных из 103, 31 июля) действительно только для прежней версии.
**Новая версия — новое измерение на следующем прогоне, до тех пор улучшение не
утверждается.**

## 4. Протокол консенсуса

Полное описание — `docs/CONSENSUS_PROTOCOL.md`. Запуск ручной:
`scripts/falsify.py`.

### 4.1 Когда обязателен

Утверждение проходит через протокол, если **одновременно**:

- содержит число или вердикт «доказано / опровергнуто», **и**
- на него будет опираться следующее решение.

Сюда попадают: пороги, пропускные критерии, «преимущество есть / нет»,
характеристики данных, на которых строится стратегия, оценки пригодности
источника.

### 4.2 Когда не требуется

Технические детали без стратегических последствий, описания поведения кода,
наблюдения с приложенным диффом или дословным фрагментом.

### 4.3 Порядок ходов — и есть механизм

```
falsify.py new NNN      создать гипотезу; Иван формулирует, указывает источники
                        → Claude пишет вердикт в H-NNN.claude.md
falsify.py run NNN      отправить фальсификатору; ответ ложится запечатанным
falsify.py unseal NNN   распечатать; не сработает без вердикта Claude на диске
falsify.py rebut NNN    второй раунд: атака на вердикт Claude
falsify.py status NNN   состояние и контроль дрейфа хэшей
```

Печать нужна ровно для одного: Claude не подстраивается под чужой ответ, а
фальсификатор не видит рассуждений предлагающего — только утверждение и числа с
источниками. **Автоматизация этого порядка его уничтожает.**

### 4.4 Известные дефекты протокола (H-001)

1. составное утверждение ломает схему — один ярлык на две конечности;
2. фальсификатор способен сфабриковать цитату с настоящим якорем;
3. запрет, записанный в системном промпте, не удерживает — фальсификатор дважды
   предложил сжечь холдаут, второй раз после прямого запрета. **Гейт должен быть
   процедурным, не текстовым.**

## 4a. Односторонние проверки подтверждают, встречный запрос различает

Когда смысл недокументированного поля устанавливается измерением, проверки
«от записи к значению» почти всегда косвенные: они совместимы сразу с
несколькими объяснениями и потому подтверждают, но не различают.

**Если у источника есть обратный вызов — он и есть проверка.** Остальное
вспомогательное.

Прецедент (`API_DIGEST.md`, `l1_address`). Пять проверок в одну сторону —
вид значения, типы счетов, отсутствие пустых, торгуют ли, распределение
размеров групп — все прошли, и все были совместимы с версией «адрес
депозита, а не владельца». В том числе обрыв распределения ровно на
документированных 8: если через мост заходили в основном одиночки, картина
та же. Различил обратный запрос `accountsByL1Address`: биржа, спрошенная с
другого конца, вернула для обычного адреса счёт-в-счёт тот же список, что
лежал в прямом справочнике, а на аномалии показала родителя, которого в
выборке не было, потому что он не торговал.

Порядок для будущих вопросов такого рода (`client_id`, persistence
`account_id`): сначала искать обратный вызов, и только потом набирать
косвенные признаки.

**Смежное правило: доли по счетам и по обороту — разные метрики.** Один
кошелёк с фермой из тысяч счетов даёт 33% выборки по счетам при 0.3% по
обороту (`API_DIGEST.md`). Всегда называть, какая метрика приводится.

## 5. Свод по API — `docs/API_DIGEST.md`

**Начат 2026-08-01** тремя записями: семантика `l1_address` (measured),
тип записи в WS-ленте (measured, с конфликтом против доки), диапазоны
`account_index` по типам. Форма ниже — как решено; наполнение по триггерам.

**Задача.** Архивариус даёт дельту. Текущее состояние технической части Lighter
не держит никто — отсюда 31 час сбора с дырой по ликвидациям при том, что тип
`liquidation` был задокументирован всё время.

**Форма — тулза, не агент.** Справочник нужен дословно; модель между читателем и
текстом — встроенный риск пересказа на каждое обращение.

**Разделение:**

- **Сборка** — редкая, только по изменившимся страницам. Архивариус уже знает,
  какие. Остальные не перебираются никогда.
- **Чтение** — `grep`/`jq` по готовому файлу. Ноль вызовов модели.

**Единица свода** несёт: идентификатор, дословный фрагмент, URL страницы,
sha256 снимка, дату извлечения. Ссылка без хэша бесполезна — страница меняется,
доказательство исчезает.

**Два источника, не один:**

- `documented` — извлечено из доки;
- `measured` — увидено на проводе.

**При конфликте побеждает `measured`, и конфликт записывается.** Причина: дока
не пишет, что массив `liquidation_trades` присутствует в каждом кадре и всегда
пуст — это измерено. И наоборот, дока может отставать от реальности.

**Триггеры пересборки** (расписания нет):

1. Архивариус сообщил об изменении конкретной страницы — пересобрать её.
2. Код споткнулся о технику: пришло значение перечисления, которого нет в своде;
   поле отсутствует там, где ожидалось. Коллектор обязан такое логировать явно,
   а не пропускать молча.

**Охват первой сборки** — то, обо что уже спотыкались: WS-каналы, объект сделки,
лимиты, эндпоинты. Проверяемая четверть полезнее рыхлого целого.

## 8. Ветки и мерж

`main` — источник истины. Работа ведётся в feature-ветках, вливается после
ревью, ветка удаляется.

Начало любой сессии: свежий клон и прогон тестов **до** чтения любого summary
(`CLAUDE.md`, §1). Параллельно могут идти сессии Claude Code — `git ls-remote`
показывает ветки, появившиеся без предупреждения.
